# Architecture

This document describes how the codebase is organised and the rules that keep it
maintainable as it grows to more cities, features and contributors.

## Overview

A single Next.js application (a _modular monolith_) deployed to Cloudflare
Workers, backed by Supabase (PostgreSQL + PostGIS, Auth, Storage).

```
Browser ──► Cloudflare Worker (Next.js) ──► Supabase Postgres (RLS enforced)
                    │
                    └──► Cloudflare R2 (page cache, photos)
```

## Multi-city (multi-tenant) routing

Every city is a row in `public.cities` and is served from its own subdomain.

| Request                  | Served by                    |
| ------------------------ | ---------------------------- |
| `<root domain>/…`        | `src/app/(root)/…`           |
| `<city>.<root domain>/…` | `src/app/city/[city]/…`      |
| anything else            | `404` (blocks Host spoofing) |

`src/proxy.ts` performs the rewrite using the pure helpers in `src/lib/hosts.ts`.
The internal `/city/*` paths cannot be reached directly on the root domain.

Adding a city is a data change only; no code changes are required.

## Layout modes

Two layouts, switched in CSS with the `desktop:` variant (`src/app/globals.css`):

- **Desktop / landscape** (≥ 1024 px wide, or a landscape screen at least
  768 × 576): filters sidebar, results and a sticky map side by side; place
  actions as buttons.
- **Mobile / portrait** (everything else, including phones held sideways):
  sticky search, filters in a bottom sheet (native `popover`), a List/Map
  toggle, and a bottom action bar on place pages.

Use `desktop:` rather than `lg:` for layout switches. Where JavaScript must
know the layout, use `DESKTOP_MEDIA_QUERY` from `src/lib/layout.ts`.

## Location ("Near me")

The browser asks for permission; coordinates are rounded to 3 decimals
(~110 m) before they are put in the URL (`?near=lat,lng`) and are never stored.

## Opening hours ("Open now")

`opening_hours` holds the OpenStreetMap text (e.g. `Mo-Sa 09:00-21:00; Su off`).
`src/lib/opening-hours.ts` parses the common subset of that syntax and returns
"unknown" for anything else, so a place is never shown as open by mistake.

- Cards and place pages show "Open · closes 9 pm" in the browser, using the
  city's `timezone`. The list page also renders it on the server.
- The "Open now" filter (`?open=now`) needs SQL, so the parsed hours are stored
  in `places.weekly_hours` (an `int4multirange` of minutes since Monday 00:00).
  The importer refreshes it; after editing hours by hand run
  `npm run hours:sync -- --city <slug>`.

## Areas (neighbourhoods)

- `npm run import:areas -- --city <slug> [--dry-run]` imports OSM
  `place=town|suburb|quarter|neighbourhood|village` points into `public.areas`.
- Every place is linked to its nearest area within 3 km (`places.area_id`),
  because most OSM places have no address. The place importer re-links after
  each run.
- The list page filters with `?area=<slug>`; a search like "cafes in Kakkanad"
  is split and redirected to `?q=cafes&area=kakkanad`.

## Emergency page

- `/emergency` on each city: tap-to-call numbers from `public.emergency_contacts`
  (country-wide rows have no `city_id`; a city can add local ones), "nearest
  hospital / pharmacy open now / police station" buttons, and places open 24/7.
- Numbers are data, not code: add or correct them with a migration.

## Admin: reviewing reports

- `https://<root domain>/admin` (root domain only; `noindex`). Sign-in uses
  Supabase Auth with email and password; the session lives in cookies that the
  proxy refreshes for `/admin` paths only.
- Public sign-ups are off. To add a maintainer: create the account in the
  Supabase dashboard (Authentication → Users → Add user, auto-confirm), then
  run `npm run admin:add -- --email <address>`.
- Who is an admin lives in `public.admins`; RLS lets a user read only their own
  row. Admins can read `place_reports` and change only `status`; a trigger
  records `reviewed_at` and `reviewed_by`. Nobody can delete reports via the API.
- Server actions re-check admin rights; the database enforces them again.

## Sharing, reporting and installing

- **Share**: the phone's share sheet when available, otherwise WhatsApp and
  "Copy link".
- **Report a problem**: anyone can report, with no account. Reports go into
  `place_reports`, which the API can insert into (only `place_id`, `reason` and
  `note`) but never read, change or delete. Row-level security accepts only
  visible places, and a trigger limits reports to 5 per place per hour and
  200 per 10 minutes overall. The form has a hidden bot trap field. Review
  reports in the Supabase Table Editor.
- **Install as an app**: each host serves its own `/manifest.webmanifest`, so
  every city installs as its own app. Icons in `public/icons` are generated by
  `npm run icons` from the site name and `src/config/brand.ts`.
- MapLibre's web worker is copied into `public/vendor` by `npm run vendor`
  (runs automatically before `dev` and `build`), because bundlers do not emit it.

## Folder structure

```
src/
├── app/            Routes only. Thin: read params, call features, render.
├── features/       Domain modules (cities, places, reviews, products, …)
│   └── <feature>/
│       ├── components/   UI for this feature
│       ├── server/       Data access and actions (server-only)
│       │   └── index.ts  Server public API
│       ├── types.ts      Domain types
│       └── index.ts      Client-safe public API
├── components/     Shared UI (ui/ = primitives, layout/ = page chrome)
├── config/         Environment validation, site identity, security headers
├── lib/            Generic helpers with no business logic
└── proxy.ts        Hostname → city routing
scripts/
├── osm-import/     OpenStreetMap importer (run with npm run import:osm)
├── area-import/    Neighbourhood importer (npm run import:areas)
├── hours-sync/     Re-derive "Open now" data (npm run hours:sync)
├── icons/          Generate app icons (npm run icons)
└── vendor/         Copy browser files that cannot be bundled (npm run vendor)
supabase/
├── migrations/     Ordered, versioned schema changes
└── seed.sql        Local development data
```

## Rules

1. **Dependencies point one way:** `app → features → lib / config`.
   Features never import from `app`.
2. **Public APIs only.** Code outside a feature imports from
   `@/features/<name>` or `@/features/<name>/server`, never deeper.
   Enforced by ESLint.
3. **Only `server/` touches the database.** Pages and components call feature
   functions; they never build queries themselves.
4. **Database rows are mapped to domain types** (`server/mappers.ts`), so
   schema naming never leaks into UI code.
5. **No hard-coded configuration.** Branding, domains and URLs come from
   validated environment variables (`src/config/env.ts`). Content such as
   cities and categories lives in the database. `process.env` may only be
   read in `src/config` (enforced by ESLint).
6. **Validate at the boundary.** Environment, form input and URL parameters are
   validated with zod before use.
7. **Security in the database.** Every table has Row Level Security enabled with
   deny-by-default policies. Application code is not trusted to enforce access.
8. **Schema changes only through migrations** (`npm run db:new <name>`), and
   regenerate types afterwards (`npm run db:types`).
9. **Caching is explicit.** Public reads use `"use cache"` with `cacheLife` and
   a `cacheTag`; mutations revalidate the matching tag.
10. **Platform code is isolated** so the hosting provider can be swapped.

## Importing places from OpenStreetMap

`npm run import:osm -- --city <slug> [--only <category,...>] [--radius <m>] [--dry-run]`

- Reads the city (centre, service radius, languages) and each category's
  `osm_tags` from the database, so adding a category or city needs no code.
- An `osm_tags` entry can join tags with `+` when all must match
  (`railway=station+station=subway` is a metro station). Categories are tried
  in `sort_order`, first match wins, so metro sits before trains.
- Features without a name are skipped unless the category has an
  `unnamed_label` (ATMs, toilets, parking, petrol pumps). Those get the label
  as their name, with the brand in front when OSM knows it ("SBI ATM").
- Features tagged `access=private` or `access=no` are skipped.
- Queries Overpass one category at a time, falling back across the servers in
  `OVERPASS_ENDPOINTS` (comma-separated) when one is busy.
- Saves each category as soon as it is fetched. If a category fails on every
  server the run continues and prints an `--only` command to retry just those.
- Upserts by `(osm_type, osm_id)`. Existing places keep their slugs (stable
  URLs) and places not sourced from OSM are never overwritten.
- When it finishes it calls `POST /api/revalidate` (root domain only, bearer
  `REVALIDATE_SECRET`, allowlisted cache tags) so pages show the new data.
  Without the secret the endpoint is disabled and pages refresh within hours.
- Data is passed to SQL as a dollar-quoted JSON literal with a random tag, so
  imported text can never alter the query.

## Data model

Implemented: `cities`, `place_categories`, `places`, `city_category_counts` (view),
and two read-only API functions:

- `find_places`: browse, search and filter in one query: typo-tolerant text
  search (pg_trgm) over name, local name, category keywords and address;
  several categories; distance from a point with an optional radius
  (PostGIS); "has phone / website / hours"; sort by relevance, distance or
  name. Plain browsing is cached by the app; text and location queries are not.
- `places_near`: places within a radius of a point, nearest first.

`find_places` also takes `p_open_at` (minutes since Monday 00:00, local time)
for the "Open now" filter. `place_reports` is the one table the API may write
to (see "Sharing, reporting and installing").

Both are `SECURITY INVOKER`, so row-level security still decides what is
visible. New API functions must be granted explicitly and added to the
allowlist in `tests/security/catalog.sql`.

Planned:

| Table       | Purpose                                                       |
| ----------- | ------------------------------------------------------------- |
| `cities`    | Tenants; one subdomain each                                   |
| `places`    | Shops, restaurants, services, landmarks (PostGIS location)    |
| `revisions` | Append-only edit history for wiki-style editing and rollback  |
| `reviews`   | Ratings and text reviews of places                            |
| `products`  | Canonical items with aliases in multiple languages            |
| `listings`  | Product availability at a place: price, stock, reported-at    |
| `profiles`  | Public user profiles and trust level                          |
| `stewards`  | Users who moderate a specific city                            |
| `flags`     | Reports of spam in user content (place reports already exist) |

## Security

- Strict HTTP security headers (CSP, HSTS, frame denial, etc.) built in
  `src/config/security-headers.ts`.
- Unknown hostnames are rejected in the proxy.
- Secrets are never exposed via `NEXT_PUBLIC_*` variables and never committed.
- Row Level Security on every table. API roles get explicit `SELECT` grants
  only; Supabase's default `TRUNCATE`/`TRIGGER`/`REFERENCES` grants and
  default function `EXECUTE` are revoked (`harden_default_privileges` migration).
- Internal `/city/...` routes are reachable only through a city subdomain.
- Each subdomain serves its own `robots.txt` and `sitemap.xml`.

### Security testing

Security checks are part of the normal workflow, not a separate step:

| Command                 | What it checks                                                                                                                                                                  |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `npm run check`         | Secret scan of every committable file, lint, types, unit tests (including the CSP builder), and `npm audit` of production dependencies                                          |
| `npm run test:security` | Against the real database and a running app: the public key cannot write or see hidden rows; the database catalog has no risky grants; headers, host spoofing, injection, leaks |
| `npm run verify`        | Both of the above. Run before every pull request and deploy                                                                                                                     |

`test:security` needs `npm run dev` running and a linked Supabase CLI. To
test a deployment, set `SECURITY_TEST_APP_URL` (and `SECURITY_TEST_PRODUCTION=1`
for production-only checks such as "no stack traces"). When you fix a
security bug, add a test here that would have caught it.
